# CRLF 行尾问题分析与修复（Windows 检出 → WSL 执行报错）

> 日期：2026-10-25 ｜ 关联提交：`ab4d180`（根目录 `.gitattributes`）｜ 影响范围：所有在 Windows 侧克隆、于 WSL/Linux 内执行的仓库脚本
> 协作规则依据：本记录按《GitHub协作规则.md》规则 4 归档；修复遵循规则 1/3/5/7（无 force push、conventional commits、不重命名变量）。

## 一、故障现象

用户在 Windows 磁盘路径下克隆仓库（WSL 挂载点 `/mnt/e/sourcecode/ai-agent-book`），执行工具包脚本时立即失败：

```text
$ ./docs/setup/select_backend.sh ollama-wsl qwen3.5:9b
env: $'bash\r': No such file or directory
env: use -[v]S to pass options in shebang lines
```

两个细节值得注意。其一，报错来自 `env` 而非 bash 自身，说明脚本根本没进入解析阶段，问题出在可执行文件的加载环节；其二，`$'bash\r'` 中带有一个回车符（`\r`），这是整个问题的指纹——Git 在检出时把行尾符换掉了，而不是脚本内容本身有错。

## 二、根因分析

### 2.1 git 的三个行尾状态

git 对一个文本文件实际上维护着三份不同的形态，行尾问题全部出在三者之间的转换上：

| 形态 | 存放位置 | 本仓库的实际状态 |
|---|---|---|
| **blob**（提交对象） | git 对象库，行尾以提交时为准 | LF（全部由 Linux 沙箱提交） |
| **索引/检出规则** | `core.autocrlf`、`.gitattributes` 决定转换方向 | Windows 侧 `autocrlf=true`（Git for Windows 默认） |
| **工作区文件** | 磁盘上的真实字节 | **CRLF**（检出时被 LF→CRLF 转换） |

`core.autocrlf=true` 在 Windows 上是安装器默认值，语义为"提交时 CRLF→LF，检出时 LF→CRLF"。这个策略对纯 Windows 工作流（记事本、Visual Studio）友好，但对"Windows 检出 + WSL 执行"的混合工作流是致命的：WSL 里的 Linux 内核不认识 CRLF。

### 2.2 shebang 为何首当其冲

Linux 内核执行 `./script.sh` 时，`binfmt_script` 模块逐字节读取首行，解析 `#!` 后面的解释器路径。CRLF 检出后首行实际内容是 `#!/usr/bin/env bash\r`——内核把 `bash\r` 当作解释器文件名交给 `env` 去查找，自然报 `No such file or directory`。此时脚本内的任何防御代码都没有机会执行，所以**这类问题无法靠脚本自身逻辑修复，只能从检出侧根治**。

值得解释的连带现象：`/mnt/*` 挂载（drvfs）默认把所有文件显示为 `rwxrwxrwx`，所以"没有可执行位"这一通常的前置错误被掩盖了，用户直接到达了 `env` 报错这一步。这也意味着在 drvfs 上不能依赖 `ls -l` 判断真实权限，而真正的 Linux 原生克隆里可执行位以 git 索引的 `100755` 为准。

### 2.3 为什么只有 .sh 受害

同一份检出里，`.py`、`.md`、`.env` 等 CRLF 都能存活：Python 解析器、dotenv、markdown 渲染器都把 `\r` 当普通空白处理。而 `.sh` 的 shebang 是内核级逐字节解析，零容忍。这就是"文档都能看、脚本跑不起来"的原因——故障面窄，反而容易被误判为脚本 bug。

## 三、证据核查（仓库侧无责）

修复前先确认问题在检出侧而非仓库侧，避免误改仓库内容：

```bash
$ git ls-files -s docs/setup/
100755 67c70493... 0    docs/setup/select_backend.sh    # 755 可执行位正确
100755 50583f38... 0    docs/setup/serve_vllm_wsl.sh
100755 b794a64d... 0    docs/setup/verify_all.sh

$ file docs/setup/*.sh
... Bourne-Again shell script, UTF-8 text executable      # 无 "with CRLF" 字样 = blob 是 LF
```

blob 内容为 LF、模式位为 755，仓库侧完全正常；`file` 输出若出现 `with CRLF line terminators` 才说明仓库内容本身被污染。这符合规则 7 的精神：先定位根因，只改真正有问题的那一层（检出规则），不顺手动无关文件。

## 四、修复

### 4.1 即时修复（存量工作区，一条命令）

```bash
sed -i 's/\r$//' docs/setup/*.sh
```

sed 只删行尾 `\r`，不触碰 git 索引；由于 clean filter 会把 CRLF 归一为 LF 再比较，`git status` 在修复前后都保持干净，不会产生行尾噪音提交。装有 dos2unix 时 `dos2unix docs/setup/*.sh` 等价。

### 4.2 根治（新增 `.gitattributes`，提交 ab4d180）

```gitattributes
* text=auto eol=lf      # 文本一律 LF 检出，覆盖各平台的 autocrlf 配置
*.sh text eol=lf
*.py text eol=lf
*.md text eol=lf
*.ps1 text eol=crlf     # PowerShell 脚本在 Windows 记事本/ISE 下更友好，例外
*.pdf binary  *.epub binary  *.png binary  ...   # 二进制显式声明防误判
```

`.gitattributes` 的优先级高于本地 `core.autocrlf`，因此**任何平台、任何 git 配置的新克隆**检出 `.sh` 都是 LF，问题不再复发。两个实现细节：一是上游 `.gitignore` 第 5 行的 `.*` 规则会忽略所有点文件，需 `git add -f .gitattributes` 强制入库（文件一旦被跟踪即不受 ignore 影响，且避免了修改上游 `.gitignore` 引入合并冲突）；二是 `git pull` **不会**重写已检出的文件（clean filter 比较后认为无变化），所以存量工作区仍需 4.1 的一次性 sed，或用下面的强制重检出：

```bash
rm docs/setup/*.sh && git checkout -- docs/setup/   # 按新规则重新落盘
```

## 五、预防与自查

- **新克隆自动免疫**：2026-10-25 之后的克隆带 `.gitattributes`，无需任何手工处理。
- **存量工作区一次性修复**：执行 4.1 的 sed 后不再复发（后续 pull 的增量文件也按 LF 落盘）。
- **快速自检命令**：`file docs/setup/*.sh | grep -i crlf` 有输出即中招；`git check-ignore -v .gitattributes` 可验证点文件忽略规则是否影响新成员。
- **给协作者的约定**：Windows 侧若用 IDE 改动 `.sh`，提交前确认编辑器行尾设置为 LF（VS Code 右下角可直接切换）；混合工作流下不建议关闭 `.gitattributes`，它让"Windows 检出 + WSL 执行"与"纯 Linux"两种姿势行为一致。
- **沉淀闭环**：本事故同步补入 `docs/setup/README.md` 第六节故障排查表首行，后续遇到同款报错可直接从排障表跳转到本文。
