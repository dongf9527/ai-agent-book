# 仓库体积调查报告：为什么 bojieli/ai-agent-book 需要 600 多 MB

> 调查日期：2026-10-25 ｜ 调查对象：`bojieli/ai-agent-book` @ `dbc046eb`（fork 同步基线）
> 方法：`du` 目录聚合 + `git count-objects` 对象统计 + `git rev-list --objects --all | git cat-file --batch-check` 全量 blob 分析 + GitHub API 核实

## 一、结论速览

GitHub 仓库页面报告的体积约 **747.6 MB**（API `size` 字段，随上游更新浮动，用户看到的"600 多 M"即此类服务器端打包体积）；完整克隆到本地后为 **2.1 GB**（`.git` 压缩包 822 MB + 检出工作区 1.3 GB）。全仓库 43,733 个对象原始未压缩总量约 3.2 GB，经 zlib 压缩后为 815 MB pack。

一句话结论：**这本书的正文（1,453 个 markdown 文件）总共只有 45.8 MB，其余 95% 以上的体积全部来自两类"非正文"资产——① 书籍成品（PDF/EPUB）的多版本历史累积，② 各章实验的运行产物（validation/runs 目录下的 JSON 轨迹、回执与截图）。**

## 二、体积去向：两个大头

### 大头 1：书籍成品的重复版本（约占 pack 的 60%）

git 按内容寻址存储，PDF/EPUB 每次重新编译都会产生全新二进制对象，旧版本永久保留在历史中。对 `git rev-list --objects --all` 全量 blob 按一级目录聚合（未压缩字节数），翻译成品目录的累积触目惊心：

| 一级目录 | blob 原始总量 | blob 数 | 说明 |
|---|---|---|---|
| `book/` | 426.1 MB | 1,249 | **其中 26 个 PDF 历史版本占 332.7 MB**，当前工作区已不含这些大文件 |
| `book-ta/` | 354.3 MB | 528 | 泰米尔语译本，多版本 PDF/EPUB 反复提交 |
| `book-en/` | 337.0 MB | 783 | 英文译本多版本 |
| `book-hu/` | 170.4 MB | 795 | 匈牙利语译本（含 20 MB EPUB 多版本） |
| `book-vi/` | 139.3 MB | 574 | 越南语译本（v1.1/v1.2 PDF 各 19.8 MB × 多次） |
| `book-ru/`、`book-zhtw/`、`book-ar/`、`book-id/`、`book-ja/` 等 | 各 50–79 MB | — | 其余 8 种语言译本，模式相同 |

仅 `book/` + 13 个 `book-*/` 译本目录的原始 blob 就约 **1.98 GB**，是 pack 体积的第一贡献者。每个译本目录在工作区的当前检出版只有 8–11 MB，历史版本才是膨胀根源。

### 大头 2：章节实验运行产物（工作区最大的四个目录）

实验目录把"运行证据"（模型轨迹 JSON、验证回执、截图、演示视频）直接提交进了仓库：

| 目录 | 体积 | 内容 |
|---|---|---|
| `chapter2/prompt-engineering/runs/` | 276 MB | 提示工程实验逐次运行记录 |
| `chapter2/attention_visualization/frontend/` | 71 MB | 含 **47.3 MB 的单个 trajectory JSON**（全库最大 blob） |
| `chapter3/user-memory/validation/` | 109 MB | `receipts.json` 单个 19 MB × 多次运行 |
| `chapter5/video-edit/validation/` + `paper-to-ppt/validation/` | 98 + 78 MB | 视频生成验证截图与剪辑 |
| `chapter10/generative-agents/validation/runs/` | 86 MB | 生成式 Agent 单次运行即 86 MB |

## 三、文件类型视角（工作区 1.3 GB）

| 扩展名 | 总量 | 文件数 | 性质 |
|---|---|---|---|
| `.json` | 691.7 MB | 2,524 | 实验轨迹/回执（可压缩，pack 中膨胀被 zlib 缓解） |
| `.png` | 160.9 MB | 896 | 验证截图（不可压缩，1:1 进 pack） |
| `.mov` + `.mp4` + `.wav` + `.mp3` | ≈ 138 MB | ≈ 1,100 | 演示音视频（不可压缩） |
| `.jsonl` | 59.3 MB | 205 | 轨迹日志 |
| `.pdf` | 52.8 MB | 42 | 当前版本成品书 |
| **`.md`（真正的书）** | **45.8 MB** | **1,453** | 正文 + 章节 + 文档 |
| `.svg` + `.py` | ≈ 32 MB | ≈ 3,800 | 图示与代码 |

## 四、机制解释：为什么 git 挡不住这种膨胀

1. **二进制无增量**：文本文件两版之间只存 diff；PDF/EPUB 重排版后整份字节序列改变，git 只能存完整新副本。`book/` 下 26 个 PDF 版本即 26 份完整拷贝。
2. **产物即证据的提交习惯**：`validation/runs` 是实验的"运行回执"，作者选择将其入库以保证可复现与可审计，代价是每次运行净增几十 MB。
3. **压缩率差异悬殊**：JSON/MD 约 4:1 压缩（3.2 GB 原始 → 815 MB pack），而 PDF/PNG/MP4 几乎 1:1，因此 GitHub 端体积主要由二进制资产决定。

## 五、对我们的意义与建议

1. **fork 无法瘦身**：fork 继承上游全部历史，GitHub 端体积会随上游继续增长。不应对 fork 做 history rewrite——那将与上游永久分叉，违反我们的 rebase 评估规则。
2. **只读内容的轻量方案**：新环境如需再次克隆，用浅克隆 `git clone --depth 1`（只取当前树，下载量约为完整历史的一半以下），或叠加 sparse-checkout 只检出 `book/`、`docs/`、目标章节目录，可把占用压到 200 MB 级。
3. **我们自己的增量保持纯净**：本仓库所有新增分析（`docs/` 下的 markdown 与 PPT 源稿）均为纯文本，不引入二进制成品文件，符合既有协作规则，不会加剧膨胀。
4. **阅读不受影响**：正文仅 45.8 MB，任何体积优化都不必动工作区文件；本轮只做调查记录，不做清理动作。
