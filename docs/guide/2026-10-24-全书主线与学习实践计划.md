## 一、贯穿全文的思路：五条主线

### 主线一：公式主线——一个公式，两种形态

全书唯一的"第一性原理"是 **Agent = LLM + 上下文 + 工具**（大脑 + 眼睛 + 手脚；学术层对应 Policy / Observation Space / Action Space）。它贯穿始终的变形是生产形态 **Agent = Model + Harness**，其中 Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正。

这条主线的三个关键判断：
- **眼睛（上下文）是决定性因素**：消融实验表明，去掉工具定义或工具执行结果会直接夺走行动与闭环能力；
- **扩展眼睛和手脚是最主要的能力杠杆**：模型固定时，重定义观察/动作空间能把不可解任务变为可解；
- **Harness 是竞争力所在**：模型能力在商品化，生产级系统中 Harness 的绝大部分代码都在做约束、验证与纠正。

### 主线二：结构主线——两大问题，三个提升层面

全书十章回答两个相互衔接的问题：**如何构建 Agent**（第 1–6 章：概念 → 上下文 → 记忆 → 工具 → 代码元能力 → 交互扩展）与**如何提升 Agent 能力**（第 7–10 章）。提升部分又分三个层面：**模型参数**（第 8 章）、**单体系统**（第 9 章）、**群体系统**（第 10 章），而**评估（第 7 章）是三者的共同前提**——先有可信信号，才谈得上提升。

各章之间不是书架式的并列，而是管道式的衔接：第 2 章管理一次任务之内的上下文；第 3 章延伸到跨会话的陈述性知识；第 4 章定义动作空间的质量；第 5 章给出"创造新工具"的元能力；第 7 章产生的评估环境和数据成为第 8 章后训练的输入、第 9 章更新提案的依据；第 9 章复用第 3 章的知识基础设施来沉淀行为经验。

### 主线三：方法论主线——把 Agent 开发从炼金术变成科学工程

第 1 章埋下"三条更新路径"：**上下文内适应（任务内）→ 外部产物更新（跨任务）→ 参数更新（训练周期）**，按可回滚程度从高到低排列。第 3 章承担发现循环的**提案**段（把一条证据变成一次最小、可审查、可回滚的修改），第 7 章承担**证据**段（失败归因决定提案有没有可依之据），第 9 章把两者合成完整闭环（学习信号 → 四载体更新 → 验证、灰度、回滚）。

串起这一切的是第 7 章的核心方法论：**观察 → 假设 → 实验 → 验证 → 新认识 → 新假设**——"没有评估，就没有进步"，Agent 工程由此从经验驱动的炼金术转向数据驱动的科学工程。

### 主线四：设计模式主线——五个模式贯穿十章

第 1 章一次性命名、后续每章复用的五个设计模式，是全书真正的"代码复用层"：

| 模式 | 一句话 | 首次大放异彩的位置 |
| --- | --- | --- |
| **提议者—审核者** | 产出与评判由不共享上下文的两个角色分别承担（自审不可靠） | 第 4 章工具事前审批/事后验证；第 5 章 PPT/视频/日志实验；第 9 章更新提案审核 |
| **渐进式披露** | 先给可检索的目录，再按需加载细节（同时优化上下文预算与选择精度） | 第 2 章 Agent Skills；第 4 章主动工具发现；第 10 章 Agent 发现 |
| **只增不改** | 状态以追加方式演进，写下不再回头改（可缓存、可重放、可审计） | 第 2 章 KV Cache 前缀稳定；第 3 章事件式记忆 |
| **边界集 + 保留集** | 每次修改同时在"应改变的样本"与"不应影响的样本"上验证 | 第 7 章回归任务与轨迹前缀边界集；第 8 章训练/评估隔离 |
| **最小 diff + 可回滚** | 每次修改尽量小、带来源、可单独回滚（让归因成为可能） | 第 3 章知识更新；第 5 章代码补丁；第 9 章更新发布 |

### 主线五：演化主线——飞轮、两朵乌云与安全观

- **飞轮**（后记）：应用层用 Harness 补上模型暂时做不稳的事 → 这些补救沉淀为下一轮训练信号 → 模型内化后对应的 Harness 层被删掉 → Harness 向新的能力前沿迁移。**模型会一层一层吃掉 Harness，但没有吃完的那一天**。Anthropic"不换模型只改 Harness，准确率 52.8% → 66.5%"的实验是这条主线最直接的注脚。
- **两朵乌云**（后记）：① Agent 如何流式、实时地与环境交互（快慢分离 / 推理提速两条路）；② Agent 如何从交互成败中持续积累经验（"小世界假设" vs "大世界假设"之争——第 3 章记忆与第 9 章进化正是对第二朵乌云的回应）。
- **安全是架构问题**（第 1 章）：护栏分上下文层、执行层、数据层三层，从第一行代码就要考虑；后续每章的安全讨论都挂在这个骨架上。
- **实践在前，命名在后**（引言）：Skill、Harness、Loop Engineering 都是业界先做后命名；赶上前沿的两条路径——足够高要求的真实业务 + 系统的评估机制。

## 三、学习实践计划：沿主线的六阶段路线

> 资源条件：有本地 GPU（第 8 章可全跑）；API 走 DeepSeek/GLM/Kimi 等。所有产出按协作规则写入本仓库 `docs/`（`docs:` 前缀提交，禁止 force push）。

### 阶段一（第 1 周）：立框架——公式与五个设计模式

- **动作**：精读第 1 章与引言；跑 `chapter1/context`，用代码指出 Harness 五要素分别对应哪些行。
- **产出**：`docs/` 提交《第 1 章精读笔记：公式三层理解 + 五模式卡片》，每个模式写清"它成立的前提"（如提议者—审核者的前提是自审不可靠）。
- **验收**：能脱稿讲出 Agent = LLM + 上下文 + 工具的缺项后果；能把任意一个 Agent 产品拆进公式的三个槽位。

### 阶段二（第 2–3 周）：眼睛主线——单任务上下文 → 跨会话记忆

- **动作**：精读第 2、3 章。实验按主线串联：`kv-cache`（只增不改的性能形态）→ `context-compression`（历史信息密度）→ `prompt-injection`（上下文层护栏）→ `user-memory`（外部产物更新 + 提案段）。GPU 加餐：`local_llm_serving` 用 Ollama 跑 Qwen3-0.6B，实测缓存命中/未命中的 TTFT 差。
- **产出**：《上下文与记忆实验记录》：六种压缩策略对比表、缓存命中数据、记忆系统生命周期图（读取 → 后台提取 → 核验 → 更新）。
- **验收**：能说清"压缩要保住任务必需的事实而非摘要流畅"；能指出 user-memory 实现里最小 diff 与来源核验在哪段代码。

### 阶段三（第 4 周）：手脚主线——工具 → 代码元能力

- **动作**：精读第 4、5 章。跑 `execution-tools`（MCP Server：参数校验 → LLM 二级审批 → 执行 → 验证全链路）与 `coding-agent`。二次开发练习：给 execution-tools 增加一个自己业务的自定义工具，走完整安全链。
- **产出**：《工具安全链路记录》：五类工具 × 设计要点表；自定义工具的 diff 与审批流截图/日志。
- **验收**：能回答"专用工具 vs 通用执行器的四个退回条件"；能解释为什么参数保真性（模型看到的参数 = 真正执行的参数）是信任边界。

### 阶段四（第 5 周）：证据主线——评估先行

- **动作**：精读第 7 章。跑 `tau2-bench-eval`（锁定 commit 的外部环境）。**核心任务**：为阶段五要做的 mini agent 预建评估集——10~20 条端到端任务 + 一组轨迹前缀边界任务，同时定义**边界集与保留集**。
- **产出**：《mini agent 评估集 v1》：任务定义四要素表、验证器设计（检查文件变化/退出状态，而非"看起来对"）、Pass@k 与 Pass^k 口径说明。
- **验收**：验证器跑通；能说清"获得一条信息"与"正确使用它"为什么是两种能力。

### 阶段五（第 6–8 周）：综合创造——mini coding agent + 后训练

- **动作**：借 coding agent 参照第 1–5 章从头实现 mini coding agent（文件系统 + 终端 + 编辑 + ReAct）。GPU 主场：第 8 章从 `cot-distillation`、`curly-quote-sft` 入手（注意 Python 3.12+，`--extra vllm`/`--extra unsloth`），理解"SFT 记忆、RL 泛化"。每个改动走阶段四的评估集，践行边界集 + 保留集。
- **产出**：《mini agent 设计文档与迭代日志》（每轮：观察 → 假设 → 改动 → 评估 → 归因）；后训练实验记录。
- **验收**：评估集上 Pass^k 可复现提升；每个失败案例都能归因到首个错误。

### 阶段六（第 9–10 周）：进化与协作——汇合点

- **动作**：精读第 9、10 章。跑 `trajectory-verifier` 与 `parallel-web-research`。为 mini agent 挂上"经验 → 知识/指令/程序"的受控更新回路（更新提案 → 审核 → 灰度 → 回滚演练）；用"新信息判据"审查是否真的需要第二个 Agent。
- **产出**：《持续进化闭环设计》：四载体的选型理由、更新提案模板、回滚演练记录。
- **验收**：一次真实失败案例经闭环转化为系统改进且评估集证明不伤保留集。

### 长期节奏（阶段六之后）：转飞轮

固定周迭代：**看失败案例 → 归因 → 提出最小 diff 改动 → 评估集验证 → 提交**。同时把 30 天 Token 到期、上游同步（fetch → merge → push）列入例行维护。
