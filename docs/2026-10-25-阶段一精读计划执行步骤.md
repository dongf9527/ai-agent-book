## 一、目标与验收标准（先明确终点）

阶段一结束时，你应能通过以下五项验收，全部可自测、无主观模糊：

| # | 验收项 | 合格标准 |
|---|---|---|
| 1 | 脱稿讲出 `Agent = LLM + 上下文 + 工具` 各缺项后果 | 缺工具=只能想不能做；缺上下文=失忆、重复劳动、无法衔接；弱模型=推理与规划受限，三者各一句话 |
| 2 | 把任意一个真实 Agent 产品拆进公式三个槽位 | 任选 Cursor / Claude Code / Manus 之一，口头说出它的三个槽位各是什么 |
| 3 | 指出实验代码中 Harness 五要素的对应行号 | 在 `chapter1/context` 的代码中定位上下文管理、工具接口、约束、验证、纠正各在哪个文件哪一段 |
| 4 | 五张设计模式卡片每张写清"成立前提" | 如提议者-审核者的前提是"自审不可靠"，只增不改的前提是"append 成本低于 rewrite 风险" |
| 5 | 完成五模式消融对照表 | 5 种上下文配置 × 任务成功率 / 失败现象，附一次复跑命令 |

## 二、第 0 天：环境准备（约 30 分钟）

仓库已在本地对齐（`main = fork/main = 5d6c1f85`），无需重新克隆。执行：

```bash
cd /home/z/my-project/repo-ai-agent-book/chapter1/context
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt        # openai/requests/pypdf/numpy/matplotlib/tabulate
cp env.example .env && chmod 600 .env  # Token 安全规则：密钥文件必须 600
```

然后编辑 `.env` 选择一家 LLM 提供商填入 API Key。实验支持 7 家云厂商（doubao / dashscope-Qwen / siliconflow / moonshot-kimi / deepseek / zhipu / openrouter）与本地 **ollama**；有本地 GPU 的话可用 ollama 拉 `qwen3:0.6b` 全程零成本跑通，无 Key 也能开始。注意本阶段**不需要 GPU 训练**，唯一用到 GPU 的章节（ch8 后训练）在阶段六。

## 三、第 1–2 天：精读引言 + 第 1 章上半——公式与三要素

**阅读范围**（`book/introduction.md` 全文 + `book/chapter1.md` 第 11–260 行）：

1. 引言的四小节：全书结构 → 如何阅读本书 → 前置知识（约 8 千字，1 小时）
2. 第 1 章上半的六小节：`现代 Agent = LLM + 上下文 + 工具` → `观察空间与动作空间` → `工具：Agent 的手脚` → `LLM：Agent 的大脑` → `上下文：Agent 的眼睛` → `ReAct 循环`（约 1.5 万字，分两个半天）

**边读边做的三件事**：

- 为"大脑 / 眼睛 / 手脚"各写一张**缺项后果卡**（对应验收 1），必须用自己的话而非抄书；
- 读到 ReAct 循环时，手动画一轮执行的序列图：读消息 → 选动作 → 执行工具 → 读工具结果 → 循环——这张图就是第 4 天跑消融实验的"预期答案"；

## 五、第 4 天：跑通 `chapter1/context` 消融实验（实验 1-1 ★★）

这是本周唯一的动手实验，目标是**用行为差异验证"上下文即眼睛"**。实验框架：一个能读 PDF、换算货币、算表达式、执行 Python 的多工具 Agent，提供五种上下文配置做消融对照。

```bash
# 1. 造样例输入并跑完整对照
python create_sample_pdf.py
python run_experiment_1_1.py          # 五种模式 × 测试任务套件
# 2. 单任务快速验证（交互模式）
python main.py
```

**观察与记录**（对应验收 5）：

1. 先跑 **Full Context** 基线，通读一条完整轨迹，确认与第 2 天画的 ReAct 序列图一致；
2. 逐个切到 No History / No Reasoning / No Tool Definitions / No Tool Results，记录：哪些任务失败、失败时的现象（重复调用？编造结果？选错工具？）；
3. 产出消融对照表：5 配置 × 成功率 × 典型失败模式，特别验证"模型自己的解释不能当作工具已执行的证据"。

**代码定位任务**（阶段一核心动作，对应验收 3）：在 `agent.py`、`main.py`、`config.py`、`grounding.py` 中找出 Harness 五要素各自的落点——上下文管理（消息列表的拼装/裁剪逻辑）、工具接口（工具定义与 schema）、约束（MAX_ITERATIONS 等上限）、验证（grounding 对结果的处理）、纠正（失败重试）。把"文件:行号 + 一句理由"写进笔记，第 3 天的猜测对不上的项是最佳学习材料。

## 六、第 5 天：五张设计模式卡片

**阅读范围**：`book/chapter1.md` 第 525–560 行"贯穿全书的设计模式"+ 本章小结。

为五个模式各做一张卡片（对应验收 4），统一模板四行：**模式名 / 解决什么问题 / 成立前提 / 在后续哪章再现**：

1. **提议者-审核者**：前提是"自审不可靠"，ch7 评估、实验的 validation 目录都是它的实例；
2. **渐进式披露**：前提是"上下文窗口有限且注意力稀释"，ch2 的核心；
3. **只增不改**：前提是"append 的成本与风险远低于 rewrite"，ch2 KV-cache 优化依赖它；
4. **边界集 + 保留集**：前提是"改进不能靠单点分数"，ch7 的评估方法论；
5. **最小 diff + 可回滚**：前提是"自我修改必须可撤销"，ch9 持续进化的安全阀。

## 八、常见坑与提示

- **不要先读完全章再跑实验**：读跑交替，公式读完就跑一次 Full Context，Harness 读完就做代码定位，记忆留存率远高于纯阅读；
- **API 报错先查 `.env`**：provider 名与 key 必须匹配（如 `LLM_PROVIDER=doubao` 配 `ARK_API_KEY`），权限 600 别忘；
- **不要跳过引言的"如何阅读本书"**：它解释了各章实验的 ★ 难度标记与依赖关系，是十周路线图的官方版；
- **上游随时在更新**：开工前 `git fetch origin && git rev-list --count main..origin/main` 确认领先/落后，我们的仓库策略以 fork/main 为准。
