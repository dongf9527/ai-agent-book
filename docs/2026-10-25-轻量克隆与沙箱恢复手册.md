# 轻量克隆与沙箱恢复手册（占位符方案）

> 背景：沙箱多次重置导致反复全量克隆（2.1 GB）成本过高。本手册确立"浅克隆 + blob 过滤 + 稀疏检出"的标准恢复流程，已于 2026-10-25 实测验证。

## 一、方案原理：git 全知道，磁盘只放需要的

git 的对象模型天然支持"占位符"：提交与树对象记录全部 11,284 个文件的路径与哈希，但 blob（文件内容）可以按需延迟获取。组合三个参数即可做到"仓库元数据完整、大文件永不下载"：

| 参数 | 作用 | 省掉什么 |
|---|---|---|
| `--depth 1` | 只取最新 1 层提交 | **822 MB 历史包**（含 book/ 26 个 PDF 历史版本等，全库 90% 的 pack） |
| `--filter=blob:none` | blob 按需获取（partial clone） | 克隆时不下载任何文件内容 |
| `--sparse` + `sparse-checkout` | 只检出选中的目录 | 未选目录的 blob 永远不会被请求（如 13 种译本 PDF、各章 runs/验证产物） |

未被检出的文件并非"不存在"：`git ls-tree -r HEAD --name-only` 仍列出全部文件（占位记录），`git sparse-checkout add <目录>` 可随时按需落地，且只传输该目录的增量 blob——这正是"占位符"语义。

## 二、实测数据（2026-10-25）

| 指标 | 全量克隆 | 轻量克隆 | 降幅 |
|---|---|---|---|
| 总占用 | 2.1 GB（.git 822M + 工作区 1.3G） | **28 MB** | ≈ 1.3% |
| 耗时 | 数分钟 | **约 3.5 秒**（clone 1.85s + 稀疏检出 1.7s） | — |
| 稀疏集 | 全部 | book / chapter1 / docs / agentbook | — |

完整性验证：HEAD = `2fb2604c` 与 fork/main 一致；docs/ 全部分析文档、两个 PPTX 成品、`chapter1/context` 实验代码、`book/chapter1.md` 均在；`git push fork main` 正常（Everything up-to-date）。

## 三、标准恢复 SOP（沙箱重置后照此执行）

```bash
# 1. 凭证与密钥（Token 安全规则：600 权限）
mkdir -p ~/my-project && cd ~/my-project
# 重建 .env（GITHUB_TOKEN/GITHUB_REPO/GITHUB_USER），chmod 600
printf 'https://dongf9527:%s@github.com\n' "$GITHUB_TOKEN" > ~/.git-credentials && chmod 600 ~/.git-credentials
git config --global credential.helper store

# 2. 轻量克隆（三个关键参数缺一不可）
git clone --depth 1 --filter=blob:none --sparse https://github.com/dongf9527/ai-agent-book.git repo-ai-agent-book
cd repo-ai-agent-book

# 3. 稀疏集：按需列出（agentbook 是各章实验共享包，必须包含）
git sparse-checkout set --cone docs book chapter1 agentbook

# 4. 仓库身份与双远端（身份必须仓库级设置，防回落全局默认）
git remote rename origin fork
git remote add origin https://github.com/bojieli/ai-agent-book.git
git config user.name dongf9527 && git config user.email dongf9527@users.noreply.github.com
```

日常按需扩展（秒级，只传增量）：

```bash
git sparse-checkout add chapter2          # 进入阶段二时
git sparse-checkout add chapter3 chapter4 # 按学习进度逐章添加
```

## 四、限制与注意事项

1. **浅克隆的历史假象**：`git rev-list --count main..FETCH_HEAD` 在浅克隆下会把上游 tip 误报为"1 个新提交"（看不到公共祖先）。判断上游是否更新，直接比对哈希：`git rev-parse FETCH_HEAD` 是否等于上次记录的上游 tip（当前为 `dbc046eb`）。
2. **历史分析需先补深度**：像《仓库体积调查报告》这类需要全历史的分析，先 `git fetch --unshallow`（一次性下载完整历史，分析完不必回退）；`--depth 1` 之外也可用 `--deepen=N` 取 N 层。
3. **agentbook 共享包必须进稀疏集**：`chapter1/context/config.py` 从仓库根导入 `agentbook.providers`（`try/except ImportError` 回退到 `parents[2]` 路径注入），缺它实验无法运行。这是 2026-10-25 实际踩过的坑。
4. **push 完全正常**：新提交的 blob 都在本地生成，push 不受 partial clone 影响；上游 fetch 用 `git fetch --depth 1 --filter=blob:none origin main` 保持轻量。
5. **单章体积预警**：需要整章时注意 chapter2（393M）/chapter3（208M）/chapter5（230M）含大量实验产物；若只为读代码，可接受 1–2 分钟的按需下载，或用非 cone 模式排除 `*/runs/`、`*/validation/` 子目录。
